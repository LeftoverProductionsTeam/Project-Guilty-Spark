### 2. New community intelligence

OpenCE Mantle's developer, leftknut, reports continued progress on a world-merging workflow in which a creator can:

- Select a base BSP.
- Select donor BSP geometry.
- Translate and rotate the donor.
- Remove unwanted faces.
- Place and merge the resulting geometry.
- Preserve donor scenery, vehicles, weapons, equipment, spawns and teleporters.

Mantle v1.0.1 publicly documents substantial portions of these operations.

Reference: https://github.com/SutlabSol/OpenCE-Mantle/releases/tag/v1.0.1

Treat the public release as the verified feature baseline and newer conversational descriptions as claims requiring implementation-level confirmation.

leftknut is also experimenting with Forge-style creation, a separate Firefight mode, and a larger island-war map.

Do not confuse Mantle editing features with engine-native multiplayer functionality.

- Player and vehicle navigation between landmasses.

#### Required world-merging workflow

**Spark source project → select base/donor → choose native or Mantle-assisted operation → position and trim geometry → reconcile objects/dependencies → validate → compile → test in Halo → return to Spark.**

When both tools support an operation, compare results objectively rather than automatically favoring Spark.

Do not invent an unsupported Mantle automation API. Start with working launch, protected file handoff, and imported-output reconciliation. Only add deeper automation through interfaces proven to exist.

Keep original maps byte-identical.

Create a clear difference between a visually assembled world, a compiled world, a player-traversable world, and a genuinely synchronized multiplayer world.

A successful map preview is not sufficient evidence.

Do not call distinct BSP transitions seamless streaming.

#### Island-war acceptance

On legal disposable sources, test the following in order:

1. Both source maps read correctly with verified source identities.
2. Donor geometry transforms preserve intended world positions.
3. Duplicated/overlapping terrain is identified.
4. New intermediate island geometry compiles natively.
5. Player and vehicle collision survives the build.
6. Native scenery, spawns, vehicles and dependencies reopen correctly.
7. At least one actual player can traverse the intended connection.
8. Two real clients can load the same map and interact with its supported multiplayer objects.
9. The map can reopen in Spark and independent native tools.

Do not advance to a full multi-island warzone until the simpler native connections and source-reconciliation tests pass.

### 4. Native Conquest/Territories authoring

The community concept is a BF-style island-control mode.

Important: Territories is not a built-in stock Halo CE multiplayer gametype. It was introduced in Halo 2.

Therefore, separate:

**Map authoring:** native CE scenario objects, spawns, capture-area geometry, references and supported scripts.

**Gametype execution:** the specific OpenCE/Chupathingy engine build or authorized mod that can synchronize capture ownership, scoring and other game-mode state.

Do not invent proprietary Halo tags or require `.yelo` for ordinary map output.

Provide visual authoring templates for:

- Capture zones.

- Score/ticket updates.

- Join-in-progress state synchronization.

Generate native scenario/HaloScript content where the selected engine supports it.

If the game mode requires native engine source changes, keep that code and dependency specific to the supported runtime. Do not disguise it as a universally supported stock Halo gametype.

Preserve user-authored sources and provide explicit native/extended-runtime compatibility labels.

### 5. OpenCE and Chupathingy are separate integration targets

Chupathingy began as an OpenCE fork but has its own maintainers, releases, platform support, hosting infrastructure and protocol-compatibility decisions.

The public repositories are the source of technical truth:

- https://github.com/OpenCommunityEdition/OpenCE
- https://github.com/ChupathingyCE/chupathingyce
- https://github.com/ChupathingyCE/chupathingyce/blob/main/docs/online.md
- https://github.com/OpenCommunityEdition/OpenCE/blob/main/docs/dedicated_server.md

Do not rely on secondhand accounts of interpersonal disagreements when making engineering decisions.

Do not infer universal cross-play from shared ancestry.

Detect and record:

- Actual executable identity.
- Pinned version and source commit.
- Runtime capabilities.
- Network protocol/version.
- Supported map editions and folder layout.
- Shared resource dependencies.
- Map identity and checksum.
- Hosting mode.
- Real multiplayer/AI support.
- Supported diagnostics and administration.
- Dedicated-server platform requirements.

### Dedicated server correction

OpenCE's official master-list approval requirement must not be confused with permission to self-host.

Its documented dedicated server can be joined directly or on LAN without public master-list approval. Do not attempt to bypass listing controls.

Chupathingy provides separate dedicated-server facilities, including Linux-based releases.

Support compatible documented hosting and server-management interfaces, but do not bypass authentication, moderation or server approval.

A server adapter must not expose unsafe arbitrary shell execution or unprotected administrative interfaces.

### Cross-play acceptance

Use version-pinned real clients and record negotiated protocol versions.

The released Chupathingy v0.8.1d documentation discusses compatibility with newer OpenCE networking, while also distinguishing older network versions. Inspect the installed binaries and their current compatibility declarations instead of hardcoding a single permanent version pair.

Validate actual two-peer joining, map checksum agreement, object interactions and reconnection.
