## 4. THE GOLDEN MAP: CREATE A HALO LEVEL FROM NOTHING

Create a fresh, uniquely named test project through Spark's real user interface.

Do not begin from a fully prepared scenario.

You may use verified legitimate Halo editing-kit resources for standard assets, but the map's authored geometry, placement, game rules and build process must originate through Spark.

### Phase A — New project

Through Spark:

- Choose the native source edition.
- Choose the target Halo runtime.
- Create an empty project.
- Select required resources.
- Verify toolchain availability.
- Establish project identity and location.
- Save, close and reopen.

Verify the creator understands what is editable source, what is generated and what is installed game content.

### Phase B — Build a world

Use the actual BSP Workshop to create:

- An outdoor playable area.
- Two enclosed rooms.
- A connecting corridor.
- A ramp.
- An elevated platform.
- At least one doorway.
- A second route between gameplay areas.
- Correctly joined structural geometry.
- Valid playable collision.
- Appropriate portals or visibility structures where native support requires them.

Use face, edge and vertex editing.

Test selection on overlapping or occluded geometry.

Test gizmo axes, snapping, extrusion, translation, surface joining, seam repair and Undo/Redo.

Use named source volumes.

Apply materials, texture scaling and UV changes.

Confirm that geometry edits do not stretch textures unintentionally or corrupt collision.

Build native geometry and independently inspect its BSP structure.

### Phase C — Import real assets from another Halo map

Use Spark's map and asset browsing interface to open a second legitimate Halo map.

Find and import representative compatible assets, including:

- A weapon.
- A vehicle.
- A scenery object.
- A door or machine.
- A biped or other suitable character asset.
- At least one shader/bitmap dependency.
- At least one compatible effect or sound dependency.

Require proper dependency resolution.

Drag imported assets into the Golden Map through Spark.

Select, move, rotate, duplicate and configure them.

Confirm native references remain valid.

Verify that incompatible asset formats produce actionable conversion or compatibility guidance rather than corrupt output.

### Phase D — Create gameplay

Through Spark's scenario and gameplay tools:

- Place multiple valid player starts.
- Configure team-specific starts.
- Add weapon placements.
- Add vehicle placements.
- Add equipment and scenery.
- Add teleporters where supported.
- Create a King of the Hill area.
- Configure suitable CTF/Oddball/Race objects where supported.
- Create an interactable door.
- Add an adjustable trigger volume.
- Configure a repeatable two-sided door event.
- Generate and inspect valid native HaloScript.
- Add environmental conditions and supported sounds.
- Add a basic objective or event sequence.

Verify placements and scenario references in independently opened native source.

### Phase E — AI and encounter authoring

Use Spark's actual AI tools to:

- Place supported AI characters.
- Create an encounter.
- Assign squads and spawn points.
- Configure activation logic.
- Set valid native behavior and applicable firing/pathfinding data.
- Add a second wave or encounter transition.
- Associate encounters with gameplay trigger events.
- Inspect generated native scenario and script data.

For runtimes without the required multiplayer AI support, validate the supported singleplayer or developer runtime behavior and record the capability boundary.

Do not claim synchronized multiplayer AI merely because local AI spawns.

### Phase F — Environment and asset fidelity

Exercise applicable:

- Sky and fog controls.
- Weather and atmospheric settings.
- Ambient sound.
- Lighting and lightmap workflows.
- Shader and bitmap editing.
- Material changes.
- Collision previews.
- Animation and model preview.
- Environment persistence.
- Detail-object preservation.

Verify source identity and native format compatibility.

Do not accept placeholder visuals as proof of game rendering fidelity.

### Phase G — Build and play

Using the user's visible Spark commands:

1. Validate project.
2. Resolve native dependencies.
3. Select the actual target toolchain.
4. Compile the scenario and assets.
5. Produce the correct runtime-specific output.
6. Independently inspect the result.
7. Launch the supported Halo game or development runtime.
8. Verify player spawn, movement and collision.
9. Visit both rooms.
10. Cross the corridor and ramp.
11. Collect and fire a weapon.
12. Interact with placed objects.
13. Use a door in both directions.
14. Confirm the scripted event works repeatedly.
15. Verify AI when supported.
16. Observe environment, textures, lighting and sounds.
17. Return to Spark.
18. Modify an object or gameplay setting.
19. Save and rebuild.
20. Confirm the revised result appears in Halo.

Record actual game load and gameplay evidence separately from compilation evidence.

**A map that merely compiles is not a passing Golden Map.**

## 9. THE AUTOMATIC FIX-AND-RETEST ENGINE

**Every reproducible failure becomes engineering work.**

Codex must not stop at writing a defect list.

For each failed acceptance scenario:

1. Record the exact user action sequence.
2. Capture the observed failure.
3. Identify the actual source revision and runtime.
4. Preserve relevant logs, screenshots and native evidence.
5. Find the root cause in the implementation.
6. Repair the existing responsible component.
7. Add a focused regression test.
8. Rerun the original failing scenario through Spark's real interface.
9. Rerun related native and integration tests.
10. Resume the interrupted Gauntlet.
11. Rerun the complete impacted journey before declaring it passed.

Continue this cycle until all supported, available test cases pass.

Never:

- Delete a failing test.
- Replace a real integration with a mock.
- Weaken native validation simply to get green results.
- Mark an operation successful merely because an API returned success.
- Disable a broken feature without accurately representing its capability status.
- Hide failures in logs.
- Pretend an external tool worked when it did not.
- Assume a runtime loaded a map without evidence.

If several failures share one underlying defect, repair the shared cause rather than issuing separate superficial patches.

Do not start unrelated feature expansion while fixing the Gauntlet.

### External blockers

If a prerequisite genuinely cannot be satisfied—missing licensed game, unavailable tool, unsupported engine feature, missing second physical machine or inaccessible hardware—record it explicitly.

State:

- The exact blocker.
- Why it is external rather than an application defect.
- Evidence collected.
- Required user action or resource.
- Tests still pending.
- What has already been proved independently.

A blocked test is neither passed nor an excuse to abandon other executable tests.

Never falsely declare the entire Gauntlet complete with unresolved mandatory blocked tests.
