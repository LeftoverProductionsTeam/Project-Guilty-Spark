# MISSION

Complete Guilty Spark's user interface into a cohesive, intuitive, highly customizable Halo development studio.

**Do not redesign the established application or replace its working interface.**

Spark already contains considerable UI engineering, native editors, workflows, rendering systems, tool integrations, application windows, menus and functionality.

Build on that foundation.

The objective is to make everything Spark already does easier to discover, navigate, use, combine, customize and return to.

A creator should be able to:

- Understand where they are.
- Know what map, asset, object or script they are editing.
- Find the relevant tools without hunting through unrelated menus.
- Switch between existing workspaces.
- Pop out workspaces into independent windows.
- Change which workspace an existing window displays.
- Work across multiple monitors.
- Open multiple maps and documents.
- Navigate between related objects and editors.
- Launch external Halo tools and return to Spark.
- Preserve editing context throughout.
- Resume previous work after closing or restarting.
- Enjoy polished, lightweight visual transitions.
- Customize their environment.
- Accomplish all this without unnecessary performance or storage costs.

**The interface should help creators understand the entire Halo development process without forcing them to understand Spark's internal engineering.**

# 2. ONE SPARK SESSION, MULTIPLE WORKSPACE WINDOWS

Use the existing Tauri application to support one coordinated Spark session containing multiple native windows.

**Do not launch three independent Spark applications simply to use three monitors.**

Windows must reuse the existing authoritative project/source infrastructure.

### Basic experience

A creator opens World Editor.

They select **Open in New Window** on Asset Studio.

Asset Studio appears as another native Spark window.

They move it to another monitor.

They open BSP Workshop in a third window.

All three remain connected to the same Spark session.

### Universal workspace switching

Each existing workspace window should support changing which workspace it displays.

For example:

**Window 1:** World Editor.

**Window 2:** Asset Studio.

**Window 3:** BSP Workshop.

The creator switches Window 2 from Asset Studio to Script Editor.

Only Window 2 changes.

Returning Window 2 to Asset Studio restores its prior editing context.

### Required controls

Integrate unobtrusive workspace-switching controls into existing headers, toolbar areas or Spark menus.

Support:

- Switch Current Window.
- Open Workspace in New Window.
- Focus Existing Workspace.
- Previous Workspace.
- Move or Reattach Workspace.
- Restore Last Workspace State.

Do not replace every window header merely to add this functionality.

Use actual workspace registration and existing routing.

Do not automatically duplicate an already-open workspace unless the creator explicitly requests another instance.

### Window independence

Each window can independently:

- Switch workspaces.
- Move and resize.
- Minimize or maximize.
- Move to another monitor.
- Restore its previous workspace.
- Close without terminating unrelated work.
- Display its own project/document context.

All windows remain part of one coordinated session.

# 4. BORROW THE BEST NAVIGATION IDEAS FROM CLASSIC HALO TOOLS

Study the actual workflows and current implementations of relevant Halo editing applications.

Useful reference categories include:

- Guerilla-style native tag hierarchy and property inspection.
- Sapien-style scenario object selection and properties.
- Eschaton/Assembly-style map and tag browsing.
- SwordEdit-style spatial manipulation.
- Modern outliner, inspector and document navigation patterns where helpful.

Verify the actual behavior of each referenced tool rather than copying an assumed feature.

**Borrow successful interaction ideas, not their entire interfaces.**

Do not turn Spark into a visual clone of another editor.

### A. Clear object hierarchy

In workspaces that edit structured content, make it easy to understand the relationship between:

- Project.
- Map.
- Scenario.
- BSP.
- Object.
- Native tag.
- Asset.
- Component.
- Property.
- Script or event.

Use existing scene hierarchies and source trees wherever available.

Improve naming, grouping and selection synchronization where necessary.

### B. Breadcrumbs

When editing deeply nested content, provide compact navigation context.

Example:

`First Contact > Scenario > BSP 0 > Corridor A > North Wall`

Another example:

`Blood Gulch > Vehicles > Warthog > Shader > Cubemap`

Each meaningful parent should support returning to the corresponding location.

Do not show enormous breadcrumb bars on screens where they add no value.

### C. Selection synchronization

Selecting an object in the viewport should identify it in the relevant hierarchy.

Selecting it in the hierarchy should focus or highlight the correct object where applicable.

Selecting a referenced native tag should make the correct asset or tag document accessible.

Ensure that source identity is preserved, not inferred from display names alone.

### D. Contextual tools

If a BSP face is selected, prioritize relevant geometry, UV, material and collision tools.

If a weapon is selected, prioritize its native tags, properties, dependencies and applicable gameplay controls.

If a trigger is selected, expose Logic / Events and associated script source.

If an AI encounter is selected, show relevant squads, behavior, activation and diagnostics.

The UI should adapt to the current task without hiding advanced functionality.

### E. Search

Preserve or extend one coherent search experience across applicable:

- Commands.
- Workspaces.
- Open documents.
- Maps.
- Tags.
- Assets.
- Scene objects.
- Installed tools.
- Relevant Learning Center content.

Search results must perform real supported navigation or commands.

### F. Related-workspace navigation

Provide contextual actions such as:

- Open in Tag Inspector.
- Edit in BSP Workshop.
- View in World Editor.
- Open Associated Script.
- Inspect Dependencies.
- Edit with Compatible External Tool.
- Build / Validate.
- Return to Previous Editor.

Make these actions appear where they naturally belong.

Do not build another global menu for every relationship.

This is one of the highest-priority UX improvements.

Preserve applicable:

- Project identity.
- Map/document identity.
- Selected object.

- Current tool.
- Inspector section.
- Camera position and orientation.
- Zoom.

- Active document tab.

- Source revision.
- Unsaved state.
- Timeline or script editing position.

Use stable IDs and the existing session/source systems.

Do not rely on transient interface element identities.

### Workspace switching

Switching away must preserve the work that was open.

Do not destroy unsaved edits.

Do not reset a viewport unnecessarily.

Do not repeatedly unload and reload the same source assets without a resource-management reason.

### Return to previous work

Add a compact **Open Work / Recent Places** interface through the existing Spark navigation.

Show:

- Current project.
- Open maps/documents.
- Open windows.
- Active builds.
- Unsaved work.
- External tool handoffs.
- Recent editing locations.
- Important failures requiring attention.

The interface may expand for complex tasks, but should remain compact by default.

### Return to Work

Example:

`First Contact / BSP Workshop / Corridor A`

Selecting this location should restore the relevant document and view, and focus its existing window if available.

If the original window was closed, restore into a suitable available window.

Do not automatically create redundant windows.

### Back and Forward

Provide meaningful location-navigation history.

Keep it separate from source Undo/Redo.

**Going Back must not undo a Halo map edit.**

Undo must not unexpectedly navigate to another project.

### Recover stale locations

If an object was deleted or a source revision changed, handle that explicitly.

Never silently jump to an unrelated object with a similar name.

# 8. FLUID WORKSPACE FADES

Add a tasteful fade transition when changing major Spark workspaces or screens.

Do this within the existing application structure.

### Behavior

- Fade the changing content region.
- Keep the stable application frame visible.
- Preserve workspace state before switching.
- Restore the destination smoothly.
- Avoid black or white flashes.
- Avoid restarting the entire app shell.
- Never lose source data during navigation.

### Accessibility

Honor reduced-motion preferences.

Offer an option to disable or reduce transitions.

Use lightweight existing CSS/React functionality where appropriate.

Do not introduce an expensive animation dependency unless the existing architecture genuinely requires it.

# 9. HALO-INSPIRED SHIELD RECHARGE DURING MODEL LOADING

Add an original, lightweight shield-recharge loading effect to Spark's existing model and complex asset previews.

**This is a preview enhancement, not a renderer rewrite.**

### Intended appearance

While a new model genuinely loads:

- Display a cached image or appropriate placeholder.
- Show a tasteful segmented shield-energy indicator.
- Animate charging as loading progresses.
- Use restrained Halo-inspired light and energy styling.
- Fade the completed model into view.
- Optionally show a brief completion pulse.

### Actual loading behavior

Connect the animation to real stages of the asset pipeline where available:

- Source/dependency loading.
- Geometry preparation.
- Textures.
- Shaders/materials.
- Animation.
- GPU resource readiness.
- First usable render.

Do not invent progress percentages.

Use indeterminate progress when the pipeline cannot accurately quantify completion.

Do not label a preview complete when required data is missing.

### Cache reuse

If a model is already available, display it immediately.

Do not replay a fake loading animation every time the creator returns.

Preserve camera and selection state.

Pause inactive previews safely.

If valid GPU resources were released due to memory pressure, reload only what is required and show the indicator during actual loading.

### Errors

Stop the animation when loading fails.

Identify the actual failure and offer meaningful recovery.

Never leave the shield spinning indefinitely.

### Customization

Respect user theme colors, sound choices and reduced-motion settings.

Use original graphics or licensed/user-owned assets.

No new heavyweight 3D effects are required for the loading indicator.

# 12. RESOURCE EFFICIENCY

Respect the P0 storage repair.

Spark Flow must not turn convenient multiwindow editing into a RAM, VRAM or disk problem.

### Requirements

- One authoritative project source.
- No full project copies per window.
- No repeated SDK extraction for workspace changes.
- Shared compatible source/dependency caching.
- Bounded memory and disk caches.
- No uncontrolled AppData growth.
- No redundant native build workers.
- No uncontrolled live runtime connections.
- Pause hidden 3D render loops.
- Preserve useful view state while releasing expensive rendering resources.
- Reuse valid model/texture data where technically possible.
- Manage GPU allocations per actual renderer context.

Independent native webviews may require independent GPU resources.

Do not falsely claim one literal renderer spans every native window.

### Performance measurement

Measure:

- Window creation.
- Workspace switching.
- Returning to a previous editor.
- Opening an already-used model.
- Loading shaders and textures.
- Preview restoration.
- Session startup.
- Multiwindow RAM and VRAM.
- Idle CPU/GPU use.
- Disk/cache growth.

Prioritize responsive operation on ordinary hardware.
