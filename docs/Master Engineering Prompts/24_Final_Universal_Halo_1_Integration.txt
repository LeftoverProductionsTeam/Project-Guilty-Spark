# PROJECT GUILTY SPARK — FINAL UNIVERSAL HALO 1 INTEGRATION & ENGINEERING BREAKTHROUGH

## ONE HALO. EVERY TOOL. EVERY WORLD. ONE WORKSPACE.

**Mission:** Make Project Guilty Spark the most cohesive, accessible, technically dependable Halo: Combat Evolved creation suite possible.

Continue from the actual current local HEAD, preserve every accepted improvement, and implement meaningful engineering advances without replacing existing working systems.

This is an implementation, integration, testing, and product-completion directive—not another speculative feature brainstorm.

### The product vision

Guilty Spark should allow a creator to:

1. Open any genuinely supported Halo 1 map or project.
2. Examine its actual geometry, objects, textures, tags, scripts, AI, and dependencies.
3. Make changes using direct cache editing, loose-tag editing, or native 3D authoring.
4. Seamlessly use compatible specialist tools without losing project context.
5. Merge worlds, add objects, build gametypes, and author campaign encounters.
6. Convert and compile for compatible Halo engines.
7. Launch the real game and verify the result.
8. Return to the same Spark project with intact source history, diagnostics, and editing state.
9. Package and share the result safely.

A beginner should not need to learn twenty applications to move a vehicle, replace a shader, or modify a weapon.

An advanced modder must still have access to the actual Halo engine structures, native tools, scripts, geometry, collision, and compiler diagnostics.

**Simple operations should be simple. Complex operations should remain possible. Neither should destroy original game data.**

# PHASE 1 — MAKE SPARK THE UNIVERSAL HALO WORKSPACE

## 1.1 Build upon the existing integration architecture

Introduce a coherent, versioned interoperability contract—internally called **SparkBridge**, unless a suitable existing system already provides the same functionality.

Do not create a parallel subsystem if existing SparkLink, runtime detection, Source Guardian, native adapters, or external-tool integrations can be extended.

Every project and operation must track:

- Project identity and original source identity.
- Source game edition and cache format.
- Input and derived-output paths.
- Source revision and checksums.
- Required shared resource maps.
- Native tag classes and dependency graph.
- Available editing operations.
- Selected compiler/build target.
- Selected game/testing runtime.
- External tool identity and version.
- Expected output artifacts.
- Changes performed and their provenance.
- Undo/rollback ownership.
- Validation and gameplay acceptance state.

Use a versioned machine-readable project manifest and capability registry. Sidecar metadata must never require proprietary modifications to Halo's native tag formats.

Do not confuse source edition, compiler target, development runtime, multiplayer host, and game compatibility.

### The critical workflow

**Spark → compatible tool → Spark → native build → target game → Spark.**

The creator must remain within one understandable project, even when an optional external application performs specialized work.

## 1.2 Create a genuinely universal tool adapter contract

Each adapter must declare:

- Supported Halo editions and data formats.
- Supported operating systems.
- Required executable/version.
- Installation discovery method.
- Supported launch arguments or verified IPC/API.
- Input types and output types.
- Whether changes are read-only, reversible, source edits, or runtime-only.
- Dependencies and compatibility restrictions.
- Output validation strategy.
- Licensing and redistribution requirements.
- Known errors and safe fallback behavior.

Provide adapter capability discovery, health checks, installation-path repair, source-aware launching, output detection, and result import.

Where an upstream tool has no supported automation interface, use a reliable GUI launch and explicit guided handoff. Never invent command-line parameters, inject into third-party processes, or claim unsupported automated control.

A tool that cannot complete a round trip must still be useful through its real supported interface.

# PHASE 3 — COMMUNITY-DRIVEN WORKFLOW REPAIR

Use the historical discussions and canonical research ledger as engineering evidence, not as claims that every report is a verified current defect.

## 3.1 mOTA-lEV: direct compiled-map editing must remain first-class

A creator must be able to perform supported map-cache changes without extracting every tag, reconstructing a loose source tree, or invoking Blender and Tool unnecessarily.

Preserve an Eschaton/Assembly-like workflow:

- Open a compiled map.
- Browse searchable tags and assets.
- Inspect exact supported fields.
- Change a safe value.
- Preview the effect where supported.
- Save a derived map.
- Verify native readback.
- Undo or roll back.

A modified field that requires tag-block resizing, new references, resource registration, or structural reconstruction must switch to a supported native build pathway.

Investigate mOTA-lEV's reported scenario-editor failures against the precise version and reproduction data available. Do not assume unspecified failures apply to every editor.

Never fake structural editing by changing only visible geometry.

## 3.2 leftknut: remove unnecessary legacy-tool complexity

The traditional workflow of extracting a map, converting to Blender, exporting JMS, compiling BSP, reconstructing tags, and rebuilding everything should be required only when the actual operation demands it.

Spark should determine the least disruptive technically correct editing route.

The user should be told:

- What can be edited directly.
- What requires compilation.
- Which companion tool is appropriate.
- What information cannot be preserved automatically.
- What will change in the output.

## 3.3 Sako and other experienced modders: intelligent Tool orchestration

Provide contextual native Tool command generation with:

- Correct edition-specific Tool executable.
- Versioned supported verbs.
- Validated arguments.
- Automatically selected source and destination paths.
- Required prerequisites.
- Expected output files.
- Real compiler output.
- Context-linked errors.

Keep the generated command visible in an expandable Advanced section.

Do not duplicate Baboon or Osoyoos features that can already be reliably invoked.

## 3.4 Renette: distinguish live edits from safe native changes

Community reports describe potential crashes and actor-state inconsistencies after certain animation or runtime tag reloads.

Exact runtime and reproduction details remain unverified.

Treat them as tests to investigate, not established Halo 1 defects.

A live update must never claim success merely because the model or biped remains visible.

Where supported, inspect actor/controller ownership, AI behavior, object counts, health, target selection, and cleanup.

Use engine-specific, approved reload mechanisms.

If a change requires a clean map restart or native rebuild, say so explicitly.

## 3.5 dunetua and the structural-editing community

Continue toward a Hammer++-quality, Halo-specific BSP authoring workflow.

Prioritize:

- Selecting real BSP faces and edges.
- Vertex/face movement and snapping.
- Geometry cutting and joining.
- Tunnel and cave construction.
- Valid collision topology.
- Portal and cluster inspection.
- Material and texture alignment.
- Lighting, fog, sky, weather, and radiosity controls.
- Tool/WRL error highlighting directly in the 3D viewport.
- Non-destructive correction previews.
- Accurate native game results.

Do not substitute editor-only mesh rendering for real Halo BSP compilation.

## 3.6 Build a Halo Geometry Doctor

Extend existing error visualizations into a contextual repair system.

Classify source-backed Tool/Sapien failures such as:

- Open edges.
- Non-manifold collision.
- Intersecting surfaces.
- Overlapping collision.
- Invalid portals.
- Out-of-bounds vertices.
- Invalid lightmap UVs.
- Invalid cluster visibility.
- Lost or displaced detail objects.
- Orphaned AI firing positions.
- Scenario palette mismatches.
- Missing referenced shaders or tags.

Highlight the precise geometry or tag causing the failure.

Offer an explanation and a previewable, reversible fix when the cause is sufficiently understood.

Never silently delete polygons, entire tag blocks, AI positions, scripts, or other content merely to make a compiler pass.

When someone wants to port an old HaloMD creation to MCC, Spark should preserve as much as technically possible and truthfully explain what must be rebuilt.

When an established tool already does the job well, Spark should integrate it rather than waste engineering effort duplicating it.

When something fails, Spark should explain the cause, preserve the source, and guide the creator toward a validated correction.

**The goal is not to claim that Guilty Spark can do everything.**

**The goal is to build the most reliable unified route to doing everything Halo 1 actually supports—and clearly identify the engineering needed to go beyond those limits.**

Protect the original vision. Respect the community's work. Reuse proven technology. Finish the strongest remaining workflows.

Make a real, measurable engineering breakthrough.

**PROJECT GUILTY SPARK — ALL THE TOOLS, AND THEN SOME.**
