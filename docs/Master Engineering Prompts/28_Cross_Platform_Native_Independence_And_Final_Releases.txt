# PROJECT GUILTY SPARK — CROSS-PLATFORM NATIVE INDEPENDENCE, MAC POLISH & FINAL RELEASE ENGINEERING

## ONE GUILTY SPARK. THREE OPERATING SYSTEMS. NO MANDATORY EXTERNAL EDITING TOOLCHAINS.

### ALL THE TOOLS, AND THEN SOME.

This is directive #28, immediately following the Mac Legacy Edition directive.

Continue from the actual current HEAD of `D:\Project Guilty Spark`, preserving every accepted implementation, original source, recovered asset, Git commit, previous-good build and research finding.

Follow `AGENTS.md`, the permanent engineering contract and the strict directive-completion gate.

Do not begin until earlier directives are accepted or explicitly deferred.

Do not create another application, abandon existing architecture or remove working capabilities to simplify packaging.

## THE MISSION

Finish Guilty Spark as a polished, downloadable application for:

- macOS — native Apple Silicon application, with Intel support where independently verified.
- Linux — native desktop application.
- Windows — native desktop application.

The application must provide its supported core Halo editing functions directly through Spark's own codebase.

**A user must not need to install Windows-only executables, Invader, Guerilla, Sapien, Halo Tool, Eschaton, SwordEdit, SparkEdit or another specialist editor just to perform the core operations Spark claims to support.**

Existing optional specialist-tool integrations should remain available where appropriate, but the supported core experience must stand on its own.

The finished product should install like a normal desktop application, launch successfully, open compatible Halo content, perform genuine modifications, export valid native results and preserve the user's original data.

No Mac App Store, Microsoft Store or Linux software repository submission is required.

Direct GitHub Releases downloads are the intended distribution method.

## 1. REMOVE MANDATORY EXTERNAL EDITING DEPENDENCIES

Audit the complete repository for dependencies on external executables and tool installations.

Include:

- Rust backend commands.
- Frontend commands and UI actions.
- Native map readers and writers.
- Tag serialization and dependency handling.
- Resource extraction and conversion.
- BSP editing and scenario placement.
- Asset importing and exporting.
- Native build orchestration.
- Game launch and testing.
- Startup and first-run setup.
- Windows-specific paths and executable names.
- CI, release packaging and automated tests.

Produce a dependency inventory distinguishing:

**A. Spark-native implementation**

Functionality fully provided by Spark itself.

**B. Bundled redistributable component**

A component whose license, architecture, size and distribution rights are explicitly verified.

**C. Optional external tool**

An independently installed program used for advanced functionality.

**D. Unsupported or blocked operation**

A capability for which a valid native implementation does not yet exist.

### Core independence requirement

Implement or complete platform-neutral native Rust functionality for supported:

- Halo cache parsing and format identification.
- Typed tag and field editing.
- Safe reference and metadata changes.
- Tag search and dependency analysis.
- Supported tag extraction and import.
- Map/resource inspection.
- Validated cache modifications and safe rebuilding.
- Scenario object placement and transforms.
- Supported gametype placements.
- Native format renaming and reference correction.
- Bitmap, sound and model inspection.
- Asset and dependency validation.
- Native export, readback and integrity checks.
- Source protection, Undo/Redo and recovery.

Reuse existing working Spark implementations.

Never introduce a second parser, editor or controller when the existing implementation can be made portable.

### External tool policy

Keep Invader, Guerilla, Sapien, Halo Tool, Blender, Baboon and other verified specialist tools as optional enhancements where useful.

Do not remove their existing working integration simply because Spark now has a native equivalent.

However:

**If a core button only succeeds when a Windows EXE or external toolkit is present, the core operation is not yet independent.**

Implement the necessary supported functionality within Spark, or accurately classify the feature as advanced/optional until independence is achieved.

Do not silently fall back to Wine, Proton, a Windows virtual machine, cloud compilation or an external service.

Do not bypass licensing restrictions by bundling proprietary editing-kit files.

## 2. CREATE A REAL CROSS-PLATFORM HALO ENGINEERING CORE

Organize existing native capabilities around one tested, reusable Rust engine.

All three operating systems should call the same underlying Halo format, project and editing implementations wherever technically appropriate.

Keep operating-system-specific code limited to:

- File and folder selection.
- Secure filesystem access.
- Window management.
- Graphics and native webview integration.
- Tool and game process launching.
- Optional external adapters.
- Installer and packaging behavior.
- Platform-specific configuration paths.

Avoid Windows-specific absolute paths, drive-letter assumptions, case-insensitive path assumptions, `.exe` requirements and backslash-only path handling in shared engineering code.

Handle macOS and Linux case-sensitive file systems correctly.

Normalize paths only when format rules permit it.

Preserve canonical Halo tag paths and original resource names without silently modifying them.

### Native data fidelity

Verify supported differences between Halo Mac Demo, Halo Full, HaloMD, Halo PC, Custom Edition, Xbox and MCC Halo 1.

Do not assume their native map formats are interchangeable.

Implement explicit format-specific readers, serializers and validators.

For unsupported source conversions or complex reconstruction, preserve an honest limitation rather than generating invalid native output.

A fully native Spark core must never become an excuse for lower fidelity.
