## 3. Build useful Halo 1 lighting diagnostics

Community reports identify severe lighting inconsistencies on custom BSPs, including actors abruptly changing brightness despite apparently correct environment lighting.

Investigate the exact Halo 1 mechanisms rather than copying Halo 3 or Reach behavior.

Reference:
https://c20.reclaimers.net/h1/tags/scenario_structure_bsp/lightmaps/

Evaluate documented Halo 1 diagnostics including:

- `debug_object_lights`
- `object_light_interpolate`
- BSP lightmap sampling for dynamic objects
- Native radiosity and lightmap generation
- Material and shader reference validity
- Lighting differences caused by source geometry or collision changes

Audit the existing Spark renderer, BSP Workshop, shader preview and native build systems.

Where missing and feasible, add a source-aware lighting diagnostic view that explains why an object may be receiving incorrect illumination.

Provide actionable suggestions based on observed native data.

Do not fabricate light probes, airprobes, shader systems or lighting controls unsupported by Halo 1.

Clearly distinguish engine-accurate evidence from an approximate Spark preview.

## 4. Improve geometry-error discovery

Modders report difficulty identifying open edges, overlapping faces, invalid BSP connections and problematic geometry when many errors are present.

Reuse Spark's existing BSP Workshop and source-geometry tools.

Improve the user workflow where genuinely needed:

- Identify native geometry validation errors.
- Highlight the exact affected face, edge, vertex or source object.
- Focus the camera on the relevant location.
- Allow selection without accidentally targeting a face behind the intended one.
- Support safe correction through existing source editing, Blender integration or native tools.
- Preserve UV/material mapping during supported geometry changes.
- Revalidate collision, portals, render geometry and native compilation.

Do not label an in-game visual diagnosis as live geometry editing.

The game may help locate the problem, but structural edits still require an appropriate source workflow and validated rebuild.

## 5. Resolve actual scenario source ownership

The community reports a case where edits in Guerilla appeared ineffective because the Halo 2 scenario used separately stored resource files.

Reference:
https://learn.microsoft.com/en-us/halo-master-chief-collection/h2/guides/guidescenarioresources

Investigate this as an edition-specific source-ownership lesson.

Before editing a native scenario component, Spark should identify the actual authoritative source file and any supported split resources, dependencies or overrides.

Where supported, show:

- Which file owns the selected data.
- Which runtime or compiler consumes it.
- Which editing tool can modify it.
- Whether the edit affects the intended native output.
- Whether an external change must be reconciled.

Never assume the Halo 2 split-resource architecture applies unchanged to Halo 1.

Do not modify unrelated source or silently merge split resources.
