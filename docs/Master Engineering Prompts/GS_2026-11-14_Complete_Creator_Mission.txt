# PROJECT GUILTY SPARK
# THE COMPLETE CREATOR MISSION
## ALL THE TOOLS, AND THEN SOME.
### ONE HALO. EVERY WORLD. EVERY TOOL. TOGETHER.

## Mission

Finish Project Guilty Spark as the most capable, safe, unified creation suite we can build for Halo 1 and compatible Halo-derived games.

Not just a launcher.

Not just a map inspector.

Not just experimental code that compiles.

**One application where a creator can open a game, modify its actual content, create something new, compile it, test it, play it, collaborate and share it.**

Existing tools remain useful and supported, but Spark must develop superior native workflows wherever practical.

Continue from the current implementation and preserve every accepted feature and previous-good build.

This mission extends Operation 110 and the original directives. It does not supersede their outstanding requirements.

## The permanent engineering rule

**User files are sacred.**

Never silently modify, replace, relocate, delete, or install into a user-owned game, map, SDK, mod or project directory.

Read-only discovery and inspection are the defaults.

Use explicit operation-specific permission for external writes. Stage automatic edits and builds separately, validate them, and maintain recoverable revisions.

Automatic external-tool synchronization may inspect changes without modifying the original files. Any conflicting or destructive adoption requires review.

A successful build must never destroy the previous-good build.

No unapproved Git publication, proprietary download, operating-system security change or destructive cleanup.

Safety failures block release.

## The execution loop

Work continuously on the highest-impact unfinished, unblocked requirement within the available execution session.

For each meaningful engineering increment:

1. Identify an actual missing capability, defect or acceptance gate in existing code.
2. Trace its implementation, UI control, dependent functions, source data and native runtime behavior.
3. Repair or finish it using existing architecture.
4. Run focused and broad regressions.
5. Verify the genuine native artifact and game behavior when available.
6. Confirm original source hashes and recoverable state.
7. Record the exact result in the existing ledger/checkpoint.
8. Continue immediately to the next dependency-respecting task.

**Do not stop voluntarily after a successful test when feasible engineering remains.**

If human input, hardware, credentials or unavailable tools block one gate, retain the exact blocker and continue another independent task.

At session interruption or resource exhaustion, save a precise bounded checkpoint so the next Codex session can resume immediately.

Do not claim asynchronous execution, invent test results or build a scheduler to keep Codex alive.

## Priority A — Finish the reliable core

Resolve current CI failures and file-protection gaps.

Complete end-to-end workflows for maps, native tags, shaders, models, collision, textures, sounds, animations, scripts, geometry, assets and dependencies.

Fix dead buttons, inaccurate labels, broken window navigation, unreliable Save/Undo and disconnected tools.

The viewport must accurately display textured, populated Halo worlds with usable selection and manipulation—not substitute shapes pretending to be game objects.

Preserve the existing single-scroll workspace preference, window independence, understandable tooltips and authentic user-provided Halo UI themes.

## Priority B — Build Spark's GPU lighting engine

Create one shared GPU lighting system with two authoring modes:

**New-map lighting:** optimized lightmap UVs, target-verified 4K pages, modern shadows, indirect light, emissive materials, per-vertex radiosity and denoising.

**Original-map relighting:** preserve original geometry, UV coordinates and page assignments where supported, with separate exact-layout and complete-relight outputs.

Allow interactive sun, lighting, fog, emissive-material and placed-light editing inside the 3D workspace.

Provide **Bake in Spark**, **Bake with Halo Tool** and **Bake with OpenTool**.

Maintain approved external tool installation, version selection, process monitoring and automatic validated readback. The creator should return to an updated Spark workspace after external editing.

Reuse existing `native_lighting.rs`, `forge_build.rs`, `haloLightmap.ts`, the bitmap readers and the native project transaction system.

Develop a memory-safe 4K path using appropriate streaming or tiling rather than removing existing allocation limits.

Compare Spark against real Halo Tool and OpenTool builds using equivalent scenes and hardware. Measure rendering accuracy, bake time, peak memory, image quality, output size and engine behavior.

OpenTool is GPL-3.0; Spark is MIT. Respect source licensing, attribution and redistribution boundaries. Do not copy GPL implementations into Spark without an approved licensing decision.

## Priority C — Universal Adaptive Export

A creator selects a target runtime. Spark automatically performs supported format conversion, asset processing and optimization needed for that runtime.

Preserve one high-quality master project and create separate native outputs.

Target every applicable Halo 1 family:

- MCC H1A Steam, Microsoft Store and applicable Proton paths.
- Chupathingy, OpenCE, OpenH1 and independently verified community engines.
- Halo PC Retail, Custom Edition and Trial.
- Original Halo Xbox, supported regions and hardware configurations.
- Mac Retail, Mac Demo, HaloMD, Intel and legacy PowerPC where feasible.
- OpenSauce and other reviewed engine extensions, including Arena Evolved and compatible dedicated servers.

**Original Xbox export is a required capability.**

Investigate and integrate Invader's existing Xbox build support, including its native `xbox-ntsc` target, before attempting a duplicate cache writer.

For a selected Xbox target, automatically adapt supported lightmaps, bitmaps, shaders, geometry, models, collision, audio, animation, dependencies, scripts and resource budgets.

Apply only verified conversions. Preserve gameplay semantics.

When a feature has no valid equivalent, identify the exact problem, offer a user-reviewed compatible alternative and refuse misleading exports. Never silently remove functionality.

Verify the result through native tools, independent readback and actual hardware/emulator gameplay separately.

Do not assume identical cache versions imply compatible rendering or networking.
