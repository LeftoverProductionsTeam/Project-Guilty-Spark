Connection requires the supplied mods-mode confirmation, no detected EAC process, one expected MCC process from the selected installation and exact reviewed EXE/Halo 1 module hashes. Subsequent access checks closed state, process creation time, image path and module base. Core operations check map/object identity, bound values and memory pages; camera/scale transactions read back writes and record incomplete rollback. Command handlers use blocking workers. `EditLock` is a Windows named mutex scoped to PID plus creation time. It serializes cooperating Spark writers, waits up to 1,000 ms and releases via RAII. Inspected operation paths acquire it before their local scale/camera/sprint state mutex. This audit did not find a specific inverted local-lock cycle or reproduce a deadlock. It is not an engine-owned synchronization point or multiplayer authority mechanism.

## Concrete limitations in the current normal write path

| Finding | Current source evidence | Consequence and required next step |
| --- | --- | --- |
| Broad target-thread suspension is normal operation | `PausedThreads::acquire` in `live_mcc.rs` enumerates and suspends up to 512 target threads over at most four enumeration passes. Resize/reset/respawn synchronization, camera apply/restore and sprint updates invoke it. | These operations are not acknowledged at a valid engine update boundary. The finite pass/thread counts are not a bound on wall-clock pause time. Keep this as explicit private-session Runtime Research Lab behavior; production integration needs an operation-specific engine-owned queue/API or another validated safe mechanism. |
| Suspension cleanup has no failure acknowledgement | `PausedThreads::drop` calls `ResumeThread` in reverse order and ignores its return value; it is the only resume path. | A resume failure cannot reach the operation receipt or circuit breaker. Do not report that every target thread resumed solely because RAII ran. Record operation-owned suspend increments and resume results; never force another owner's suspend count to zero. |
| Spark failure can bypass cleanup | The suspended-thread handles/resume bookkeeping live inside Spark's stack guard. | Abnormal process termination can skip the only resume calls. This is a source/API-derived failure mode, not a locally reproduced frozen-game incident. An isolated writer process alone does not establish crash-safe target recovery or engine-safe timing. Do not normalize this mechanism merely by adding a helper. |
| Enumeration does not close thread creation | A pass with no newly observed thread IDs is accepted, followed by application memory reads/planning/writes. | No engine handshake prevents a new target thread or in-flight work after the final enumeration. “All observed threads paused” is not a proved atomic engine transaction. Replace this assumption rather than advertising it as atomic. |
| Preparation occurs while paused | `scale` acquires the pause guard before `scaling::resize`; resize then calls `snapshot`, which scans up to 2,048 object slots and performs per-object/tag reads before planning and applying fields. | The pause includes inspection, allocation, planning, writes/readback and possible rollback. Structural caps do not prove acceptable latency. Profile actual pause duration and phase cost only in an explicitly suitable owner-controlled test; move bounded preparation outside the critical section and revalidate at a real engine boundary in the replacement design. |
| Disabled controllers continued taking the edit mutex; C34 repair below | The inspected version slept 40 ms, acquired `EditLock`, then inspected camera/sprint enabled state. The camera's active update cadence was separately limited to 120 ms; scale keeper checks every 300 ms. | Started-but-disabled controllers could each attempt roughly 25 mutex acquisitions per second while their owner objects remained alive. This is source cadence, not a measured FPS/CPU regression. The new local scheduling gate removes those idle acquisitions and exits closed workers; it does not validate engine timing. |
| Session suitability is not positively attested | `connect` accepts a boolean mods confirmation and checks for known anti-cheat process names. | These checks do not independently establish private versus protected matchmaking, host authority or all anti-cheat states. New write capabilities need positive, operation-specific session suitability evidence; do not derive it from an absent process name, build hash or selected launch option alone. |

Microsoft documents [`SuspendThread`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-suspendthread) as debugger-oriented and unsuitable for ordinary thread synchronization, including a possible deadlock when a suspended thread owns needed synchronization. This audit does not establish such a concrete target-held-lock cycle in Spark's current calls; the broad suspension and missing boundary are the confirmed design limitations. [`ResumeThread`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread) returns explicit failure/suspend-count information that is currently ignored. Rust documents that [`process::abort`](https://doc.rust-lang.org/std/process/fn.abort.html) skips destructors, explaining why the guard cannot supply an abnormal-exit recovery guarantee.

The named mutex also accepts `WAIT_ABANDONED` as ownership. Windows documents that abandoned-mutex protected state needs a consistency check in [`WaitForSingleObject`](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject). Existing operation identity/readback checks are useful, but the code has no shared cross-process journal identifying an interrupted writer's operation-owned mutations or suspended threads. Do not restore another instance's guessed snapshot after abandonment; detach and require normal recovery when ownership/safe restoration cannot be established.

## Narrow controller scheduling repair

`live_controller_poll.rs` now performs a local preparation check, releases the controller state mutex, acquires `EditLock` only for requested work, and rechecks closed/enabled state or ticket revision before running any process transport. This preserves the existing edit-lock-before-state-lock order in the transport section. A queued poll cannot reapply after a preceding disable or write after the session was permanently closed. Disabled states with pending restoration/errors are retained rather than cleared or repeatedly restored by idle polling.

Sprint's background worker needs transport only while enabled. The inactive camera worker still samples keyboard/focus locally so F6 can enable it; it does not acquire the shared edit mutex or read a game process without a valid press edge. Explicit status/configuration requests retain their existing inspection behavior. Enabled camera periodic work remains at the existing 120 ms cadence. Explicit camera configure/toggle/shortcut/restore advances a local revision, rejecting a queued shortcut ticket from an older configuration. Explicit restore paths and their byte operations remain unchanged, and workers exit promptly after the existing successful disconnect closes the session.

Meaningful fake-lock/transport tests cover disabled and restore-pending polls, enabled-to-disabled queued work, closed-at-entry/closed-while-queued, stale shortcut tickets, preserved pending state on lock failure and release of the local state mutex before waiting for `EditLock`. Camera tests exercise its actual preparation/ticket functions, preserving inactive F6 edges, held-key behavior, due-state checks and pending errors. A core fake-memory regression verifies that sprint reset and camera restore restore original bytes once and repeated restoration performs no additional writes.

Validation: `cargo test -p guilty-spark live_` passed **8 tests**, with the actual-game disconnect test still opt-in/ignored. `cargo test -p spark-core --lib live_adapter` passed **33 tests**, including real core operation logic against synthetic memory. The Windows self-process read test is not a Halo session test. The scheduling change needs a focused owner-controlled MCC check of F6, disable/restore, Shift sprint and disconnect; no new actual-game acceptance is claimed. Earlier C33 observations remain historical evidence for their tested versions.

## Further remediation and acceptance gates

Retain exact profile/lifetime/map/object checks and read-only discovery. Do not add generic memory-write endpoints, arbitrary remote execution, forced game termination, code-patching guesses, broad suspension as production architecture or protection bypasses. Keep unverified operation capabilities unavailable independently while other runtime work continues.

The next safe implementation slice is a narrow operation contract with generation, preconditions, bounded fields, an engine-owned apply boundary, acknowledgement and operation-owned restoration. Measure end-to-end and critical-section latency on the supported build. Test closed game, stale handles, respawn/map change, abandoned writer, apply/readback failure, resume/failure handling where relevant, disconnect and aborted helper without writing into a new generation. A harness can validate failure routing; it cannot establish engine timing or actual game recovery.

No live performance numbers, session suitability, successful recovery from external termination or new actual-game write acceptance are claimed here. The [connected-world audit](C34_CONNECTED_WORLD_AUDIT.md) independently covers file/cache structure and private gameplay gates; it does not validate this memory transport.
